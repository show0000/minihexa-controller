# miniHexa Mac 컨트롤러 & 시뮬레이터 — 설계 문서

작성일: 2026-11-12

## 1. 의도와 이유

사용자는 Hiwonder miniHexa(Standard 키트, ESP32 기반 18DOF 육족 로봇)를 가지고 있다. 공식 PC 소프트웨어는 Windows 전용이고, 사용자에게는 Mac만 있다. Mac에서 **블루투스 Xbox 호환 컨트롤러로 로봇을 조종**하고, 로봇 없이도 동작을 확인할 수 있는 **3D 시뮬레이터**를 원한다.

사용자가 하고 싶은 것 (사용자 발언):
1. 로봇을 제어해서 이동시키기
2. 계단(높이 3cm 미만의 턱) 오르기
3. 춤 등 정해진 동작 시키기
4. 특정 움직임을 녹화하고 재생하기
5. 한 동작씩 짜서 새 춤 만들기

## 2. 목표 / 비목표 / 안티목표

**목표**
- Chrome 웹앱 하나로 Intel 맥과 Apple Silicon 맥 모두에서 동작
- 게임패드 → BLE → 공식(출고) 펌웨어로 실시간 조종. 펌웨어 수정 없이 동작
- 같은 명령을 받아 움직이는 3D 시뮬레이터 (로봇 없이 연습, 녹화 미리보기)
- 컨트롤러 입력(=로봇 명령)을 시간 순서대로 녹화, 저장, 재생
- 한 동작(자세)씩 짜서 새 춤을 만드는 편집기. 시뮬레이터로 미리 보고, 로봇에 저장해서 컨트롤러 버튼으로 실행
- 3cm 미만 턱 오르기를 시뮬레이터에서 실험하고 실기로 검증

**비목표**
- 공식 Windows 소프트웨어 기능 전체 이식 (서보 편차 보정 UI 등). 춤 편집기는 예외로 범위에 포함
- 확장 모듈 (AI 비전, 음성, 터치, 도트 매트릭스) — Standard 키트에는 없음
- 물리적으로 정확한 시뮬레이션 (질량, 마찰, 서보 토크). 시뮬레이터는 기구학 기반 시각화
- 펌웨어 교체 (1·2단계 기준. 3단계에서 필요성이 드러나면 별도로 논의)

**안티목표 (기술적으로 동작해도 실패로 보는 것)**
- 연결이 끊기거나 컨트롤러를 놓았는데 로봇이 계속 걸어가는 상황. 정지 보장이 최우선이다
- Intel 맥(Chrome 150 고정)에서만 깨지는 기능
- 설치 과정이 복잡해서 Mac을 바꿀 때마다 개발 환경을 세팅해야 하는 상황

## 3. 제약

### 3.1 플랫폼
| 맥 | macOS | Chrome |
|---|---|---|
| Intel | 12.7.4 Monterey | **Chrome 150에서 업데이트 중단** (Google 공지: 150이 Monterey 마지막 버전) |
| Apple Silicon | 27.0.1 | 최신 |

→ **Chrome 150에 있는 웹 API만 사용한다.** Web Bluetooth, Gamepad API, Web Serial, File System Access, IndexedDB, WebGL2는 모두 150보다 훨씬 이전부터 있다.

→ Web Bluetooth와 Web Serial은 **보안 컨텍스트**(https 또는 `http://localhost`)에서만 동작한다.

### 3.2 펌웨어 프로토콜 (출처: `vendor/app_firmware/remote/`)

공식 Google Drive "2.3 APP 프로그램" 폴더의 출고 펌웨어 소스. 핵심 파일은 `ble_server.cpp`, `uart_server.cpp`, `remote.ino`.

**공통 형식**: ASCII 텍스트, 필드는 `|`로 구분, 명령 끝은 `&`. 숫자는 부호 있는 10진수로 보낸다 (펌웨어가 `atoi` → `uint8_t` → `int8_t`로 처리하므로 -50도 정상 동작).

**BLE**
- 기기 이름 `miniHexa`, 서비스 `0000ffe0-0000-1000-8000-00805f9b34fb`
- 쓰기 특성 `0000ffe1-…` (WRITE), 알림 특성 `0000ffe2-…` (NOTIFY)
- 로봇 → Mac: 200ms마다 `$<배터리mV>$<초음파거리>$`
- 펌웨어가 `&`가 나올 때까지 버퍼에 이어 붙이므로, 20바이트 단위로 나눠 써도 된다

| 명령 | 의미 | 값 범위 / 비고 |
|---|---|---|
| `C|vx|vy|r&` | 이동 | vx, vy: -50~50 (펌웨어가 ±3.0으로 매핑). r: 0=회전 없음, 1=왼쪽, 2=오른쪽 (이산값. 제자리면 ±2.5, 이동 중이면 ±0.2) |
| `F|yaw|pitch|roll|x|y|z&` | 몸체 자세 | yaw, pitch, roll, x, y: -50~50. z(높이): 0~30. 높이에 따라 pitch/roll 허용 각이 커짐 |
| `K|1|n&` | 동작 실행 | 1: 비틀기(반시계), 2: 비틀기(시계), 3: `_wake_up`, 4: `wake_up`, 5: 애교. 그 외 번호는 로봇에 저장된 동작 그룹 |
| `H|r|g|b&` | 초음파 센서 LED 색 | 0~255 |
| `I|1&` / `I|0&` | 자동 장애물 회피 켜기 / 끄기 | 다른 BLE 명령이 오기 전까지만 유지 (아래 참고) |
| `J|1&` / `J|0&` | IMU 균형 유지 켜기 / 끄기 | 다른 BLE 명령이 오기 전까지만 유지 (아래 참고) |
| `O&` | 리셋 (기본 자세) | |

**USB 시리얼** (115200bps, 같은 텍스트 형식). BLE 명령 외에 다음이 추가로 있다.
- `L|n|tL|tH|id|dL|dH|…&`: 서보 n개 직접 제어 (시간, ID, duty)
- `M&`: 18개 서보 duty 읽기 → `M|1|d|2|d|…&`
- `K|3|…&`: 동작 그룹을 로봇에 저장. `K|2&`: 동작 중지
- `G|…&`: 서보 편차 보정
- 1초마다 `A|<배터리>&` 송신

**중요한 동작 특성**
- **BLE와 USB는 동시에 쓸 수 없다.** BLE가 연결되면 펌웨어는 BLE 명령만 처리하고 USB 명령(`L` 포함)은 무시한다 (`remote.ino`의 `ble_server.state` 분기).
- **회피(`I`)와 균형(`J`)은 "마지막 명령"으로만 유지된다.** 펌웨어는 BLE 명령을 하나만 저장하고, 새 명령(`C`, `F`, `H`, `K`, `O`)이 오면 덮어쓴다. 정지 명령 `C|0|0|0&`도 마찬가지로 모드를 끈다.
- **내장 동작과 동작 그룹은 실행 중에 끊을 수 없다.** 펌웨어 루프를 붙잡고 실행된다 (`wake_up`은 약 9초, `twist`는 수 초). BLE에는 중지 명령이 없고(`K|2`는 USB 전용), 동작 중에 보낸 명령은 마지막 하나만 동작이 끝난 뒤 실행된다.
- **동작 그룹 (춤 저장 형식)**: 로봇 SPIFFS의 `/ActionGroup<id>.rob`에 저장된다. id는 0~50, 프레임은 최대 254개. 파일은 [총 프레임 수 1바이트] 다음에 프레임마다 58바이트 `frame_index|control_num|time_l|time_h|(id|duty_l|duty_h)×18`이 이어진다. 저장은 USB `K|3|…&`로 하고 (`uart_server.cpp`, `Robot::action_group_download` 참고), 실행은 BLE와 USB 모두 `K|1|id&`로 한다. **단, id 1~5는 펌웨어가 내장 동작으로 가로채므로 직접 만든 춤은 6~50번에 저장해야 한다.**
- **서보 duty와 관절 각도의 관계**는 소스에 있다 (`hiwonder_robot.cpp` `set_angle`, 대략 29~160줄): duty = 500 + k·각도, 반대 방향이면 2500 − k·각도. 180° 서보는 k=11.11, 280° 서보는 k=7.14. 중립은 140°. 관절별 방향과 서보 종류도 같은 곳에 있다. 다만 역기구학 각도의 기준(0°의 위치)은 바이너리 안에 있으므로 실기로 확인해야 한다.
- **이동은 래치된다.** `C`를 한 번 보내면 다음 `C|0|0|0&`이 올 때까지 계속 걷는다. → 정지 보장 로직이 필수다 (§4.5).
- Wi-Fi 경로(SSID `hiwonder`에 접속하는 TCP 9023 포트)는 브라우저에서 원시 TCP를 쓸 수 없으므로 사용하지 않는다.

### 3.3 로봇 기구학 (출처: `vendor/kinematics/`, `hiwonder_robot.h`)
- 다리 마디 (cm): 첫째 마디 2.85, 둘째 마디 3.70, 셋째 마디 7.2
- 다리 부착 위치 (몸 중심 기준, cm): L1 (3.15, -5.65), L2 (4.34, 0), L3 (3.15, 5.65), L4 (-3.15, 5.65), L5 (-4.34, 0), L6 (-3.15, -5.65)
- 몸체 7.6 × 14.0cm, 서보 중립 140°, 기본 다리 들어올림 3cm, 최대 반 보폭 3cm
- 걸음새: 삼각 보행(tripod gait). 1·3·5번 다리와 2·4·6번 다리가 사인 궤적으로 교대한다 (`hiwonder_robot.cpp` `Robot::update`)
- 역기구학(IK)은 컴파일된 라이브러리(`kinematics_lib.a`)라서 소스가 없다. 시뮬레이터에서는 위 치수로 3DOF IK를 직접 구현한다

## 4. 결정된 사항

### 4.1 형태
Chrome에서 여는 **단일 웹앱**. 로봇 연결 화면, 시뮬레이터, 녹화가 한 화면에 있다.

### 4.2 연결 모드
- **BLE 모드 (기본)**: 조종, 동작, 녹화, 재생. 1·2단계는 BLE만으로 완결된다.
- **USB 모드 (3·4단계)**: Web Serial로 연결. 서보 직접 제어, 춤을 로봇에 저장, 턱 넘기 걸음새 실험. BLE와 동시에 쓸 수 없으므로, USB 작업 중에는 BLE 연결을 끊도록 안내한다.
- **로봇 없음 모드**: 시뮬레이터만. 연결이 없어도 앱 전체가 동작한다.
- 명령은 언제나 시뮬레이터로도 같이 전달되어, 실기와 화면이 함께 움직인다.

### 4.3 녹화와 재생
- 녹화 단위는 **게임패드 입력이 아니라 로봇에 보낸 명령 + 타임스탬프**다. 매핑을 바꿔도 녹화본이 깨지지 않는다.
- 재생할 때 같은 시간 간격으로 명령을 다시 보낸다 (실기, 시뮬레이터, 또는 둘 다).
- 저장 위치: 브라우저 안의 녹화 목록, 그리고 Mac에 JSON 파일로 내보내기와 불러오기 (두 맥 사이에서 옮길 수 있도록).

### 4.4 춤 편집기 (사용자 결정: 한 동작씩 짜기)
- 춤 = **자세(키프레임)의 목록**. 자세마다 18개 서보 값과 이동 시간을 가진다. 로봇의 동작 그룹 형식(§3.2)과 1:1로 대응한다.
- 편집은 시뮬레이터 위에서 한다. 다리나 관절을 골라 각도를 바꾸고, 자세를 추가, 복제, 삭제, 순서 변경할 수 있다. 전체를 시뮬레이터에서 재생해 미리 본다.
- [작성자 판단] 기본 편집 수단은 관절 슬라이더. 발끝을 끌어서 자세를 잡는 방식(앱의 IK 사용)은 있으면 좋은 기능으로 둔다.
- USB로 연결되어 있으면 편집 중인 자세를 실기에 바로 보내 볼 수 있다 (`L` 명령).
- 완성한 춤은 USB로 로봇의 6~50번 칸에 저장하고, 컨트롤러 버튼에 연결한다. 이후에는 BLE로 `K|1|id&`를 보내 실행한다.
- 춤은 JSON 파일로 Mac에 저장하고 불러올 수 있다. 녹화 파일과 함께 두 맥 사이에서 옮길 수 있다.
- [작성자 판단] 녹화(고수준 명령)를 춤(서보 값)으로 자동 변환하는 기능은 범위 밖이다. 펌웨어 IK를 정확히 재현해야 하기 때문이다.

### 4.5 턱 넘기 (4단계, 실험)
- 1차 시도: BLE만으로 몸을 최대 높이(`F … z=30`)로 올리고 저속 전진. 효과를 시뮬레이터와 실기에서 확인한다.
- 2차 시도: USB `L` 명령으로 다리를 더 높이 드는 전용 걸음새를 앱에서 계산해서 전송한다. 시뮬레이터에 높이를 조절할 수 있는 턱을 두고 발끝 궤적이 턱과 충돌하는지 먼저 확인한다.
- 성공을 보장하지 않는 실험 기능이며, 결과에 따라 범위를 다시 논의한다.
- [작성자 판단] 2차 시도에는 실기 보정 세션이 필요하다. 역기구학 라이브러리가 바이너리라서 각도 규약을 모른다. `M&`으로 읽은 duty와 앱의 IK를 맞춰 봐야 한다. 서보 직접 제어 후에는 펌웨어의 걸음새 상태와 실제 자세가 어긋나므로, 턱을 넘은 뒤에는 항상 `O&`(리셋)으로 복귀한다. 세부 계획은 1·2단계가 끝난 뒤 따로 세운다.

### 4.6 배포 (사용자 결정: 인터넷에 올리기)
- 정적 웹앱을 **GitHub Pages**(https)에 올린다. 두 맥 모두 설치 없이 주소만 열면 된다.
- [작성자 판단] Pages를 무료로 쓰려면 저장소가 공개여야 한다. **`vendor/`(Hiwonder 펌웨어, 라이브러리 원본)는 저장소에 올리지 않는다** (`.gitignore`). 앱 코드에는 프로토콜 상수만 들어간다.
- 개발 중에는 개발 Mac(Apple Silicon)의 localhost에서 실행한다.

### 4.7 게임패드 (사용자 결정: 버튼 직접 지정)
- 컨트롤러는 정품이 아닌 Xbox 호환 제품이고, 버튼 배치는 Xbox와 같다.
- **버튼 지정 화면**을 둔다. "이동 축을 움직이세요", "비상 정지 버튼을 누르세요"처럼 기능마다 차례로 입력을 받아 축과 버튼 번호를 기록한다.
- 지정한 결과는 브라우저에 저장하고, 파일로 내보내고 불러올 수 있다. 처음 실행할 때 지정 기록이 없으면 지정 화면으로 안내한다.
- 지정할 수 있는 기능: 이동(전후, 좌우), 회전(왼쪽, 오른쪽), 기울이기, 높이, 비상 정지, 리셋, 회피 토글, 균형 토글, LED, 녹화 시작/정지, 동작 버튼(내장 동작이나 저장된 춤 번호를 연결).

### 4.8 안전 (정지 보장)
다음 상황에서 즉시 `C|0|0|0&`을 보낸다.
- 스틱이 중립으로 돌아왔을 때
- 게임패드 연결이 끊겼을 때
- 브라우저 탭이 숨겨지거나 포커스를 잃었을 때
- 재생을 중지했을 때

그 밖에 비상 정지 버튼(화면과 컨트롤러 모두)을 둔다. 연결이 끊긴 경우에는 앱이 보낼 방법이 없으므로, 로봇이 계속 걷고 있었다면 화면에 경고를 표시한다.

**[작성자 판단] 끊을 수 없는 동작 처리**: 내장 동작을 실행하는 동안에는 조종 입력을 잠그고, 화면에 "동작 중 (n초)"을 표시한다. 그 사이 눌린 비상 정지는 동작이 끝나는 즉시 보낸다. 이 제약은 UI에서 사용자에게 알린다.

### 4.9 [작성자 판단] 회피 / 균형 모드
펌웨어 특성(§3.2) 때문에 두 모드를 **배타적 모드**로 다룬다. 모드를 켜면 앱이 상태를 "회피 중" 또는 "균형 중"으로 바꾸고, 그동안 스틱 입력을 보내지 않는다. 스틱을 조작하거나 다른 버튼을 누르면 모드를 끄고 일반 조종으로 돌아간다 (UI에 표시). 녹화에는 모드 켜기와 끄기도 하나의 명령으로 들어간다.

## 5. 빌더에게 맡기는 것

- 기술 스택 세부 (언어, 번들러, 3D 라이브러리). Three.js 정도의 WebGL 라이브러리면 충분하다
- 버튼 지정 화면의 세부 UX. 지정 화면에서 제안할 기본 배치는 왼쪽 스틱=이동, LB/RB=회전, 오른쪽 스틱=기울이기, 트리거=높이, A/B/X/Y=동작, 메뉴=회피 토글, 보기=균형 토글, 오른쪽 스틱 누르기=리셋, 십자키=LED 색 정도
- 춤 편집기의 화면 구성 (타임라인 모양 등)
- 명령 전송 빈도 (값이 바뀔 때만 보내고, 20Hz 이하로 제한하는 정도를 권장)
- 시뮬레이터 걸음새는 펌웨어 `Robot::update` / `cal_omni_move_end_point`의 삼각 보행을 근사하는 수준이면 된다
- 화면 레이아웃과 디자인
- GitHub Pages 배포 자동화 방식 (Actions 등)

## 6. 단계

1. **조종**: BLE 연결, 버튼 지정 화면, 게임패드 조종, 내장 동작 버튼, 배터리와 거리 표시, 시뮬레이터 동기화, 정지 보장, GitHub Pages 배포
2. **녹화와 재생**: 녹화 목록, 파일 내보내기와 불러오기
3. **춤 편집기**: Web Serial(USB) 연결, 서보 값과 시뮬레이터 각도 대응 (실기 보정 세션 포함), 자세 편집과 미리보기, 로봇에 저장(6~50번 칸), 버튼 연결
4. **턱 넘기 (실험)**: 3단계의 USB 서보 제어를 바탕으로 턱 넘기 걸음새 실험

각 단계가 끝날 때마다 사용자가 실기로 확인한다.
